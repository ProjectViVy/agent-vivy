# VIVY Web and TUI I18N Design

> Status: core Web/TUI I18N implemented (Tasks 1–7, Task 9 closure);
> Go/TUI execution and whole-repository CI verification remain blocked by
> unavailable toolchains. Task 8 is deliberately deferred by the recorded
> 2026-09-09 authority ruling; plugin I18N remains a non-normative proposal.

## Decisions

- English (`en`) is the product default locale.
- The developer/self-host project may set `VIVY_DEFAULT_LOCALE` in its local
  root `.env`. The repository already ignores `.env` and `.env.*` files; no
  local environment file is committed.
- `vivy-sdk pack` resolves that developer default and records it in the built
  Generation settings. A sealed Generation therefore has an immutable default
  locale independent of later source-tree changes.
- The user can change the locale from Settings. That choice is stored in the
  global VIVY workspace `settings.yaml`, so Web, TUI, and VIVY CODE share it.
- The initial supported locale set is exactly `en` and `zh`. The catalog and
  RPC shapes must remain extensible to additional locales later.
- Proposed plugin catalogs would be owned by plugins and use the same
  translation-unit and key/argument contract as core VIVY; this is not an
  implemented or normative SDK capability (see the Task 8 ruling below).

## Goal

Provide complete, consistent English and Chinese user-interface localization
for the Web and TUI faces, with one backend-authoritative locale setting and a
plugin boundary that does not require a monolithic core dictionary.

## Non-goals

- Do not translate user-authored text, model output, tool output, Journal
  content, generated plugin content, or arbitrary workspace files.
- Do not add runtime catalog discovery, network catalog downloads, or a
  plugin permission boundary for localization.
- Do not make the browser's localStorage the source of truth. It may cache the
  last known value for startup continuity only.
- Do not change the language of protocol method names, error codes, structured
  fields, or machine-readable identifiers.

## Effective locale and precedence

The global workspace `settings.yaml` user override wins over every default.
Without an override, the startup modes differ:

- A sealed Generation uses its immutable embedded default; neither the
  process environment nor `.env` is consulted.
- An unsealed development body uses the process `VIVY_DEFAULT_LOCALE`, then
  the local root `.env` value, then the compiled product default `en`.
- Packing a new Generation resolves process → root `.env` → `en` and embeds
  the result. The workspace preference is not baked into the artifact.

An empty workspace value means “no user override”; it must not be serialized as
an invalid locale. Only `en` and `zh` are accepted in this release. An invalid
environment or Generation value is rejected during build/startup rather than
silently selecting a partially translated catalog.

`.env` is a developer input, not a user preference. The unsealed development
startup and packing paths may read the root `.env` for `VIVY_DEFAULT_LOCALE`
without overriding an already-set process environment variable. A sealed
Generation uses its embedded value and does not change behavior because a
different source-tree `.env` happens to exist. The loader must parse only the
supported non-secret setting and must never log or persist arbitrary `.env`
values.

```dotenv
VIVY_DEFAULT_LOCALE=en
```

An already-set but empty or unsupported process value is rejected; it does
not fall through to `.env`. Only `en` and `zh` are valid explicit defaults.
The locale loader reads this one non-secret setting, not arbitrary dotenv
configuration. `.env` and `.env.*` remain gitignored.

## Backend and Generation contract

### Shared workspace settings

`internal/app/settings.Settings` carries an optional locale override:

```yaml
locale: zh
```

The empty value means that the Generation default applies. Existing settings
files without this field remain valid and resolve to the Generation default.
The existing atomic `Load`/`Save`/`Update` behavior and global workspace path
remain unchanged.

### Generation default

The existing Generation/assembly metadata carries a presentation settings block:

```json
{
  "recipe": {
    "settings": {
      "locale": "en"
    }
  }
}
```

`vivy-sdk pack` obtains the locale from the effective developer default,
embeds it in the generated executable through the existing build-overlay
mechanism, and writes the same value to `generation.json`. The committed source
body embeds `en`. The manifest and executable must not disagree.
This core presentation metadata does not establish v1 Module identity,
selected-Module artifacts, or plugin catalog provenance in the current SDK.

### Control-plane API

`settings/get` exposes:

- `locale`: effective locale;
- `generation_locale`: immutable Generation default;
- `workspace_locale`: saved user override, or empty;
- `locale_read_only`: whether this deployment cannot persist settings.

The narrow `settings/locale` write method accepts payload
`{ "locale": "en" | "zh" }`. It must update only the locale field in the
shared settings document, preserve every unrelated overlay, validate the value,
and return the same locale view as `settings/get`. A deployment without a
settings path returns the existing read-only conflict without changing the
document. A frozen provider session may still change the locale: freezing
protects the provider/model environment, not presentation preferences.

The backend is authoritative after a successful write. Web and TUI clients
must refresh or apply the returned effective value rather than assuming a
local write succeeded.

## Web implementation

The existing `ui/src/i18n` store remains the rendering API (`t`, locale
subscription, interpolation), but its source of truth changes:

1. Start with the compiled English fallback, or a valid last-known localStorage
   cache, so the shell can render before the first RPC response. Browser/system
   language is not an authority.
2. Hydrate from `settings/get` during application initialization.
3. When the user selects a language, call `settings/locale`; apply the
   returned effective locale after success and retain only a localStorage cache
   for startup continuity.
4. Update `document.documentElement.lang` and Intl date/number formatting from
   the effective locale.

All human-readable Web UI copy must resolve through the catalog. Existing
`zh.ts` and `en.ts` dictionaries may be reorganized, but they must remain
structurally complete and use identical keys and placeholders. Hard-coded
labels, button text, empty states, toasts, errors, command descriptions,
accessibility labels, and settings copy must be migrated. The completeness
check must inspect the maintained catalog source rather than the obsolete
`ui/src/app/i18n-additional.ts` path.

## TUI implementation

The TUI must resolve the same semantic keys and arguments as Web. The
translation data should have one canonical catalog shape and generated or
validated Go accessors so a key cannot silently exist in only one face.

The TUI resolves catalog keys and named arguments through
`sdk/tui/i18n`. Its English/Chinese Go catalogs have parity and placeholder
validation tests; Web has its own paired TypeScript catalogs and completeness
command. Locale values and backend settings authority are shared.

`scripts/i18n-cross-face-contract.json` is the canonical schema for semantic
units shared by Web and TUI. Each unit has one stable semantic ID, the Web and
TUI projection keys, and one named-argument set. The cross-face checker loads
both locale projections, enforces key and placeholder parity, and rejects
unclassified face-specific units. Every face-only Web and TUI key is declared
exactly in the same schema; broad root or namespace exemptions are not
accepted. This makes interface-specific copy intentional and causes any new or
removed key to fail until its classification is reviewed. `just i18n-check`
executes both the Web completeness audit and this cross-face conformance check.

The TUI obtains the effective locale through the same control-plane settings
view during startup. For an in-process face, the same backend settings path is
used; for `--live`, the RPC result is used. The TUI renders its chrome,
commands, status messages, errors, prompts, help text, and accessibility-like
descriptions through the locale resolver. Conversation/user/model text remains
untouched.

If the settings RPC is unavailable, TUI falls back to the embedded Generation
default and reports a sanitized warning through the existing error path; it
does not invent a second persisted locale. Web, TUI, and VIVY CODE share the
global preference, not automatic cross-process live-push updates.

## Proposed plugin I18N contract (non-normative; Task 8 deferred)

The recorded Task 8 authority ruling deliberately defers implementation. The
current SDK is the rejected v0 experiment, whose name/directory identity and
separate plugin/face projections cannot stand in for normative v1 Module IDs
and selected-Module artifact provenance. PLG-P1 is still `UNSCHEDULED`; the
v1 Descriptor/Assembly/artifact implementation is a prerequisite. No v0
extension, compatibility path, fallback identity, or ad-hoc artifact mapping
is authorized. The complete core Web/TUI localization requirement is unchanged.

After that foundation exists and this extension is explicitly accepted and
scheduled, a v1 Module descriptor could declare an owned catalog. This example
is proposal metadata only, not an accepted descriptor field or working SDK API:

```json
{
  "i18n": {
    "catalog": "i18n/catalog.json",
    "default_locale": "en",
    "locales": ["en", "zh"]
  }
}
```

Catalog keys are namespaced:

- Core VIVY owns `vivy.*`.
- A plugin would own `plugin.<module-id>.*`, derived from its approved v1
  Module ID; no v0 name-to-owner mapping is defined here.
- A plugin cannot override core keys or another plugin's keys.

Each translation unit contains a stable key, locale messages, placeholders,
and description/context. Optional short/long forms are presentation variants of
one semantic unit. Descriptor-based plugin UI sends `label_key` and
`label_args`, never a pre-rendered locale-specific label. Full-code UI Modules
receive the same host localization surface.

The proposed SDK validator would verify catalog schema, supported locales,
namespace ownership, duplicate keys, and placeholder parity. Selected catalogs
are explicit Generation inputs; their content hashes enter Generation provenance. Runtime
resolution uses active locale → plugin default locale → safe key/diagnostic
fallback. None of this plugin validation, catalog provenance, host plugin API,
or runtime plugin UI support is implemented by Tasks 1–9. See
`docs/plans/plugin-platform/README.md` and the non-normative
`docs/architecture/VIVY-PLUGIN-SPEC.md` §7.1 for the resumption boundary.

## Testing and acceptance

The implementation is complete only when:

- Go tests cover locale validation, `.env`/process precedence, Generation
  embedding, settings persistence, read-only behavior, and RPC round trips.
- SDK pack tests prove `generation.json` and the embedded default agree and
  invalid locale input fails closed.
- Web tests prove English is the default, backend hydration wins over stale
  localStorage, settings changes persist, both catalogs have equal keys and
  placeholders, and no maintained UI key is missing.
- TUI tests render representative chrome, commands, errors, and prompts in
  both locales and prove the same settings value drives both faces.
- Once the v1 prerequisite and scheduling are satisfied, plugin verification
  tests must cover valid catalogs, namespace collisions, missing locale
  entries, placeholder mismatches, and selected-Module provenance. These are
  deferred acceptance requirements, not passing core coverage.
- `go test ./...`, `cd ui && pnpm test`, `cd ui && pnpm typecheck`, and the
  repository CI command pass after the full migration.
