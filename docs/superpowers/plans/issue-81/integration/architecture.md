# Architecture reconciliation and decisions

This is an integration addendum to existing approved contracts, not a new product design. [Epic #81](https://github.com/ProjectViVy/agent-vivy/issues/81) and its owner boundary govern scope. Existing architecture and plans cited in source-audit.md remain authoritative; update their status only during later authorized implementation. This plan does not copy stale status claims as acceptance.

## Chosen architecture

Reuse the existing Skill revision and Review Center authority, recover the existing optional ACP Face through FaceHost/Control, and selectively transplant still-applicable #32 repairs onto the pinned main. This preserves one Service.Run, durable Journal, Policy/Grant path and core Storage migration owner. Wholesale merges would restore stale host contracts and overwrite later main fixes; rebuilding the features would create duplicate mechanisms. Small adapters at existing boundaries provide the required behavior with less maintained code and no extra service, scheduler, cache or runtime.

## Eino capability check

Main pins Eino `v0.9.13`, OpenAI EinoExt `v0.1.13`, Claude `v0.1.25`; #80 proposes Eino `v0.9.21`. Main's `internal/runtime/model_stream_observer.go` already uses `model.BaseModel`, `schema.StreamReader`, `schema.Pipe` and propagates mandatory `End` failures. The retired proof uses `compose.NewWorkflow`, `Workflow.Compile` and `schema.RegisterName`; W9 removes its production caller rather than adding orchestration. Skill discovery uses the existing Eino Skill backend behind Vivy domain interfaces. ACP uses protocol `acp.BaseAgent`, `conn.NewAgentConnectionFromTransport`, `transport/stdio.NewTransport` and the fork's `WithAgentMaxPendingDispatch`, `WithAgentShutdownTimeout`, `WithAgentSanitizedErrors`, `WithAgentConnectionLabel`.

These API uses were inspected in repository/branch source and the repository skill. No upstream Eino module cache was found or installed in this planning environment; no claim of fresh SDK execution is made. Before any future adapter code, verify the exact chosen candidate's pinned upstream source. No new LLM orchestration capability is proposed. Journal CAS, approval policy and storage authority remain Vivy-owned; Eino provides no substitute authority. Any new Provider/orchestration request absent from the pinned surface is `DEFERRED-INDEFINITE` under repository rules, not a reason to add custom machinery.

## Lifecycle, persistence and performance

Skill recovery reads existing revision/approval state and hashes intended bytes; no per-token scan or new background loop. ACP has connection-local bounded queues and IDs, not durable adapter state; teardown keeps host Control alive until owned runs are cancelled/reconciled. Cognitive intent uses the existing CAS snapshot; only final source-bound composition selects dependency pins. Diagnostics bounds reads before materialization and clips the complete JSON envelope. No new dependency/service/cache is justified by these repairs; no latency/RSS benefit has been measured here.

Core Storage alone owns any required SQL migration and its paired dialect files. The peer's proposed migration 046 remains exclusively E5 review scope. Neither these plans nor E6 approval payload metadata require an invented migration. Generated Assembly and UI staging are regenerated by existing tools, never manually edited.

Exclusions: DIVA installation/UI/voice/Mentle acceptance; #6/#7/#60-63 scheduling; EvoMap; full AgenticModel migration; #57/#66 runtime capability claims; new content publication. BML phase one is the parent package's acceptance target, not a prerequisite to redesign memory here.
