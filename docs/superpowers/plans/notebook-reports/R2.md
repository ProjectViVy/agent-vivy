# R2 — Report Generation, Provenance and Feedback UI Implementation Plan

> For agentic workers: REQUIRED SUB-SKILL: use `superpowers:executing-plans` for sequential execution, or `superpowers:subagent-driven-development` only if selected by the owner. Use checkboxes to track implementation steps.

**Goal:** Let users generate reports, edit their bodies, understand coverage and feedback, and safely inspect/adopt regenerated candidates.
**Architecture:** Extend N3's existing notebook view and editor with R1 actions and authoritative Run/provenance projections. Do not create a second report page, polling service or local task ledger.
**Tech Stack:** React/TypeScript, existing module-action client and Run subscription facilities, Vitest, split-UI Playwright.
**Spec:** [Design](../../specs/2026-10-09-notebook-reports-design.md), sections 5–9.
**Requirements:** NB-03, NB-04, NB-05, RP-02, RP-03.
**Status/dependencies:** [Package index](index.md).
**Global Constraints:** Inherit index and UI rules. R1 owns report DTOs. Report controls derive from backend capabilities; generic notebook editing must work without reports.
**Review Focus:** generated versus edited claims; candidate adoption conflicts; exact included feedback; truthful empty/partial/fallback status; reconnection and absent capability.

## Interface and state contract

Consume `vivy.reports.generate/get/cancel/settings.read`. R3 later supplies settings.write, so this Story displays admitted/default settings but does not fake editable schedule settings. Generate accepts period, current/completed/historical window selector and stable operation key; it never submits a prompt, graph, trusted scope, arbitrary tools or report body as facts.

Use one Run ID returned by admission to drive progress, refresh and cancellation through existing host subscriptions or bounded status reads. Reconnect by Run ID and operation receipt; do not infer failure from an interrupted WebSocket. Show original generated source provenance only under the corresponding revision. Edited content is visibly user-authored and unvalidated by that evidence.

## Task 2 — Present provenance, candidates and feedback honestly

**Modify:** N3 `revisions.tsx`, `comments.tsx`, `editor.tsx`, new `reports.tsx` and tests/catalog.

- [ ] Add failing cases for full, empty, partial, truncated and fallback provenance; show period, IANA timezone, window/as-of, missing coverage, categorized fallback reason and source references independently of editable Markdown.
- [ ] Display generated original versus human revision clearly. Candidate revisions offer `View generated version` and `Use this version`; adoption sends expected version and operation key through N1 action. A stale adoption preserves both candidate and current head and opens the conflict flow.
- [ ] Show included feedback by exact ID/version/body snapshot and source document. Editing/resolving the live comment does not rewrite a prior run's included feedback. Label `included` rather than promising the model followed it.
- [ ] Distinguish original source facts from labeled user comments/human-edited context. Do not render a source-validation badge on edited prose or make an unsupported correction appear source-backed.
- [ ] Use existing safe Markdown/link behavior, loading/error/empty states and EN/ZH catalog. Paginate revisions/comments; avoid fetching every report's body to render the list.
- [ ] Run `pnpm --dir ui test` and `pnpm --dir ui typecheck`; verify editing a report, reading its original, and returning preserves unsaved content.

- [ ] Add a deterministic provider barrier so Playwright can pause generation. At `:3015`, generate a daily report, edit its body, add a comment, regenerate, and prove new output is a candidate while edited head survives. Inspect exact included comment version.
