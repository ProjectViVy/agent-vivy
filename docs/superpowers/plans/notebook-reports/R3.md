# R3 — Report Scheduling, Recovery and Lifecycle Implementation Plan

> For agentic workers: REQUIRED SUB-SKILL: use `superpowers:executing-plans` for sequential execution, or `superpowers:subagent-driven-development` only if selected by the owner. Use checkboxes to track implementation steps.

**Goal:** Schedule completed-period reports through the existing cron authority and prove deterministic restart, cancellation, capability deactivation and publication recovery.
**Architecture:** Extend existing CronJob report payload/Service dispatch introduced in R1. Existing workflow revisions, Run/Journal, epoch fences and output receipts remain the only execution authority. No report timer, queue, worker ledger or duplicate settings store.
**Tech Stack:** Go, existing cron expression/scheduler, INOFY recovery, SQLite/PostgreSQL, report control actions; minimal settings UI integration after R2.
**Spec:** [Design](../../specs/2026-10-09-notebook-reports-design.md), sections 9–11, 13, 16.
**Requirements:** RP-03, RP-04, RP-05, NB-05.
**Status/dependencies:** [Package index](index.md); backend work depends on R1. Final REPORTS Epic acceptance also requires accepted R2 UI evidence.
**Global Constraints:** Inherit index. No silent re-billing after ambiguous inference. Schedule disable, report capability disable and UI omission have different documented effects.
**Review Focus:** DST/calendar identity; duplicate/overlapping triggers; bounded catch-up; crash after publication; shutdown/omitted Generation recovery.

## Settings and scheduling contract

Use R1's sole `(scope, period)` CronJob record and revision. Disabled rows retain manual defaults. `vivy.reports.settings.write` performs CAS plus idempotency receipt in one Storage transaction (reuse the notebook mutation receipt mechanism under a report-settings operation kind, not a new execution table). It validates authorized target section, existing provider catalog selection, IANA zone, schedule and immutable series ownership. Generic cron updates must not bypass typed report validation or mutate its trusted scope.

Scheduled operation identity is scope + series + period + UTC window + timezone + configuration revision; use a canonical bounded digest as operation key. Target identity excludes config revision so regenerating a period cannot create a second period document. Automatic windows are completed calendar periods; manual current windows retain admitted as-of. Settings changes apply only to new admissions.

At restart, admit at most the latest missed completed period per enabled daily/weekly/monthly schedule. Record skipped ranges through existing structured Journal/event projection and show them in status. CronJob durable next-run state and workflow admission receipts decide what is missed/already admitted; process-local `active` state is an optimization only. There is no catch-up fan-out for every missed date.

**Eino/INOFY capability check:** Reuse pinned INOFY RunStore recovery/fencing. Eino Generate itself provides no durable exactly-once remote billing guarantee; ambiguous narrative attempts become recovery_required under existing workflow projection. Do not build a second model-retry scheduler to conceal that limit.

| Durable evidence at recovery | Required behavior |
| --- | --- |
| No admission commit | New same-key admission may create one Run |

| Publication receipt committed | Reconcile that revision even if acknowledgement was lost |

## Rollback and limits

Disable schedules first to stop new automatic admissions. Preserve the database and Run/provenance records; switch to a notebook-only artifact only after lifecycle reconciliation. Older binaries require a pre-migration backup, not a schema downgrade. A report marked recovery_required requires explicit operator reconciliation/new attempt; hiding it or retrying an ambiguous model call is not recovery.
