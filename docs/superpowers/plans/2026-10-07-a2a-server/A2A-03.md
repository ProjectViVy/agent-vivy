# A2A-03 — Ordinary Answer and Recovery Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans or explicitly selected superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Accept an ordinary remote answer atomically and resume the existing native Run while preserving local-only approval authority.

**Architecture:** Extend the native Question transition transaction, not the protocol adapter. Reuse Eino's existing checkpoint resume through Service; the durable answer, actor, Journal event and external receipt commit together.

**Tech Stack:** Go 1.26.4, native QuestionStore/Journal, SQLite/PostgreSQL, existing Eino `Runner.ResumeWithParams` integration.

**Spec:** [Design sections 6 and 9](../../specs/2026-10-07-a2a-server-design.md), baseline `58d1143` plus adopted G0 revision.

**Epic / requirements:** E1 / R3, R8. **Status/dependencies:** [index](index.md#epics-and-story-authority).

## Global Constraints

Apply [package constraints](index.md#global-constraints). The actor is `channel:a2a:<principal>`. A2A content never writes ApprovalStore. Both ordinary answer and local answer must participate in the same native transition discipline; external retries resolve their receipt before current question/state checks.

## Review Focus

RF1/RF3: join answer parts then TrimSpace before canonical hashing; CAS the captured Question, never a later question. A crash after consuming an answer cannot leave it parked forever or re-execute effects without proof.

### Task A2A-03.1: Atomic shared Question transition

**Files:** Modify existing `internal/runtime/service.go`, `payloads.go`, `internal/storage/contracts.go`, backend `questions.go`/`journal.go`; extend A2A-02's `internal/storage/channel_tasks.go` and backend counterparts. Create (proposed) `internal/storage/question_transitions.go`, `internal/runtime/channel_task_answer_test.go`; version `schemas/events/payloads/user.question_answered.json`. Preserve readability of local version-1 events.

**Interfaces:** Extend ChannelTaskStore with `CommitChannelTaskAnswer(context.Context, ChannelTaskAnswerCommit) (ChannelTaskCommitResult, error)` as design 6.1 specifies. It wraps the same backend transaction helper used by a new optional native `QuestionTransitionStore.CommitQuestionTransition(context.Context, QuestionTransitionCommit) (QuestionTransitionResult, error)` for local answer/cancel/expiry. `QuestionTransitionCommit` contains RunID, QuestionID, Outcome (`answered`/`cancelled`/`expired`), Answer, Actor, Reason, At and the runtime-built Event. Result contains Changed and committed Events. External `ChannelTaskAnswerCommit` adds Scope, MessageID, InputHash and the exact captured pending Question ID; it commits its receipt in that same transaction. This is one transition implementation with two native callers, not two competing state machines.

- [x] **Step 1:** Write backend/runtime `TestChannelTaskAnswerAtomicRace(t *testing.T)` with barriers around transaction entry. Assertions:

```text
local answer / remote answer / expiry / Run terminal race => one valid winning transition
remote winner => answer + channel actor + answered event + receipt all committed
rollback at any write => Question remains pending and no receipt/answer event survives
duplicate accepted answer after resume/terminal => original receipt, no second resume
two fresh IDs targeting one captured question => loser cannot answer a later question
Run/context mismatch or approval-required => no answer receipt
TrimSpace(join(parts, "\n\n")) => same canonical stored/hash text part
```

- [x] **Step 2:** Run `go test ./internal/storage/sqlite ./internal/storage/postgres ./internal/runtime -run 'ChannelTaskAnswerAtomicRace|Question' -count=1 -v`. Expect the current split Question/Journal behavior to fail the atomic assertion.
- [x] **Step 3:** Implement transaction-local transition/append helpers. PostgreSQL must use the existing `pg_advisory_xact_lock(hashtextextended(runID, 0))`; a row lock alone does not serialize with Journal.Append. Follow scope -> Session -> native Run lock -> Question CAS order where those locks are needed. SQLite acquires write ownership before reads. Require a pending/unexpired matching question and no committed Run terminal; append the versioned answered envelope and receipt atomically. Route local answer/expiry/cancel through the same discipline; preserve legacy backend APIs for other existing callers without duplicating side effects.
- [x] **Step 4:** Repeat with `-race -count=1`, including real PostgreSQL independent connections and native local-question regressions. Expect no duplicate answer or inverted-lock deadlock. Validate both old/new payload schemas and exact actor attribution.
- [x] **Step 5:** Commit the native transaction: `feat(runtime): accept channel answers with atomic native transitions`.

### Task A2A-03.2: Resume, crash settlement and approval exclusion

**Interfaces:** Complete TaskID-targeted dispatch in SubmitChannelTask. Consume committed answer result and call the same native resume handoff used by local answers. No direct Eino call from ChannelHost/plugin, no new executor lease or recovery daemon.

- [x] **Step 1:** Write `TestChannelTaskAnswerCrashRecovery` and `TestA2AApprovalIsLocalOnly`. Assert the same Run either follows proven native recovery or receives one durable classified failure; no consumed-answer indefinite wait. Send `/approve`, `/deny`, `/pending` and metadata-like answer text; none may approve a tool or enter chat command parsing.
- [x] **Step 2:** Run `go test ./internal/runtime -run 'ChannelTaskAnswerCrashRecovery|A2AApprovalIsLocalOnly|ServiceRecover|AnswerQuestion' -count=1 -v`; expect missing dispatch/recovery behavior to fail.
- [x] **Step 3:** Schedule resume only for a newly committed winning answer. Use the existing checkpoint/native execution owner. First-cut unproven resumption after process loss settles as native failure, retaining answer evidence; never silently retry tools. Pending approval remains local Face-owned; native expiry/cancel must settle no-Face cases. A completed/failed/canceled task is never reopened.
- [x] **Step 4:** Repeat recovery tests and `just ci`. Expect one durable terminal at most, accepted answer identity retained, local approval still functional and no remote approval mutation. A fresh subsequent turn may create a new task in the same context only after terminal settlement.
