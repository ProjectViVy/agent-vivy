# Acceptance

A reviewer can distinguish three separate decisions: approving this documentation,
scheduling the component spike, and accepting a later product migration.

The revised plan must not imply that an isolated Eino test covers Vivy's Journal,
UI or checkpoint persistence; that a constructor proves endpoint/model capability;
that component probe bytes are the product binary delta; or that code rollback
alone restores resumability across Eino versions.

Expected reader outcome: required capability gaps block adoption, cost tradeoffs
require explicit acceptance, existing runtime availability/feature checks remain,
and the migration has concrete history, attachment, reasoning, usage, checkpoint
and real-path UI gates without introducing a new codec or runtime framework.
