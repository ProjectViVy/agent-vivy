## Real-binary startup smoke (config parse → validate → composition)

Built `vivy-smoke.exe` from the worktree (`go build -o $TEMP/vivy-smoke.exe
./cmd/vivy`) and ran it with `VIVY_CONFIG` against scratch configs under the
user temp dir; SQLite path and bundle_dir pointed into scratch / worktree
fixtures. The root tree's `data/` was never touched.

1. Valid config with `execute_max_timeout_seconds: 210`:
   process starts, listens on `127.0.0.1:8791`, `GET /` → HTTP 200,
   log line `vivy starting addr=127.0.0.1:8791`.
2. `execute_max_timeout_seconds: 601` → exit 1, `startup aborted` with
   `runtime.execute_max_timeout_seconds must be between 1 and 600 seconds`.
3. `execute_max_timeout_seconds: 0` → same rejection as (2).

## UI-editable ceiling: live split-loop smoke (127.0.0.1:3015)

Split pair: backend binary from the worktree (`go build -o $TEMP/vivy-dev.exe
./cmd/vivy`, `VIVY_CONFIG=config.dev.yaml`, cwd = worktree, port 8787) plus
`cd ui && pnpm dev` (port 3015, `/rpc` proxied to 8787). Dev data root
resolves to the worktree's `data/` (SQLite at `data/vivy.db`), so the
operator settings document lives at `data/settings.yaml` in the worktree —
not `data/agent-home/` (that is the default path used only when the data
root is empty).

1. Settings → 通用 renders the 执行超时上限 card (input, range hint,
   保存通用设置 button; the input reflects the persisted override and the
   placeholder the config fallback).
2. Typing 120 into the field and submitting through the real React form
   handler (Playwright's physical click is unreliable in this IAB session —
   actionability times out on every element including the shipped model tab,
   so the submit was dispatched on the form and confirmed via
   `preventDefault` + the resulting file) wrote
   `data/settings.yaml` with `execute_max_timeout_seconds: 120`. This
   exercises the actual `submitSettings → saveSettings → settings/update`
   path.
3. `settings/get` over the page's own RPC channel echoed
   `execute_max_timeout_seconds: 120` /
   `config_execute_max_timeout_seconds: 30` before restart.
4. Restarting the backend with the same config applied the overlay at
   startup: log line `settings overlay applied ... execute_max_timeout_seconds=120`.
5. After restart `settings/get` reports
   `execute_max_timeout_seconds: 120` and
   `config_execute_max_timeout_seconds: 120` (the fallback now reflects the
   overlaid ceiling), and a `settings/update` echo carries the config
   fallbacks (`config_provider`, `config_model`,
   `config_execute_max_timeout_seconds`) so the UI state stays consistent
   right after a save.

Cleanup after the smoke: the worktree `data/` scratch (settings doc + SQLite)
was left out of commits; `routeTree.gen.ts` regenerated by `ui-ci` was
restored (content-identical, autocrlf-only noise).
