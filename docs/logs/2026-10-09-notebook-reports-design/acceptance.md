# Design acceptance

The owner can review one design document and determine:

1. What ships in the notebook release independently of reporting.
2. Which module owns content, report generation, UI, and persistence authority.
3. How Markdown edits, generated originals, comments, candidate revisions,
   conflicts, deletion, and retry behave without losing user content.
4. Which scoped action/tool contracts are new, which existing facilities are
   reused, and which Host/compiler bridges must be implemented.
5. Why ordinary chat does not automatically read the notebook, and how reporting
   avoids automatic memory/persona changes and self-ingestion.
6. How manual and scheduled reports share INOFY/Service/Journal authority.
7. Which acceptance cases and repository gates an implementation must prove.

The draft awaits written-spec approval. Proposed increments are not executable
Story plans and are not marked Ready. Reviewing this design does not imply
approving code execution, repository-instruction changes, external publication,
or any deployment.
